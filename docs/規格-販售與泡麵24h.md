## 一、一句話定位

**穿線櫃（22 格）＋販售櫃（2 櫃）＝ 24h 無人店**：客人隨時「寄拍穿線／取拍」＋「買羽球用品／泡麵」，同一套系統（同後台、同 LINE、同 RS-485 硬體介面）。

## 三、販售櫃（2 櫃）設計

### 3.1 硬體（485 級聯方案，2026-08-21 定案）

- **板型**：每櫃 1 片 **UPUS-SKB36-V1.2（36 路）**，30 路用、6 路備用（比 2 片 18 路省一顆位址）。
- **櫃號**：新增 **df-f、df-g** 兩櫃（全新櫃，不改裝停用的 df-b~e）。
- **現場機器**：已改裝 **Win10**（2026-08-21）；**方案 A 定案**——kiosk 畫面住雲端（`smartlocker-alpha.vercel.app` 全螢幕 Chrome），SkbBridge 仍本機管 485 開格（見 `kiosk/README-kiosk.md`）。
- 每櫃格數/尺寸依商品定：羽球用品（球、握把布、拍線、飲料）＋泡麵（碗麵）。
- **485 串接（級聯，一條鏈到底）**：

```
Win7 kiosk (USB-485 CH340)
   │ A/B/GND
   ▼
[df-a] SKB25 位址1 (22格) ──級聯座2──> [df-f] SKB36 位址2 (30格) ──級聯座2──> [df-g] SKB36 位址3 (30格)
   ▲                                      ▲                                      ▲
電源 PSU#1                               PSU#2                                   PSU#3
終端：主機端 120Ω                       （中間不接）                            最後一片：A/B 端子 120Ω 焊盤跳線
```

- **定址**：撥碼值 = 位址 − 1（全 off = 位址 1）。現有板維持 1；新櫃 1 = **2**（撥 00001）、新櫃 2 = **3**（撥 00010）。5-bit 撥碼上限 32 片，3 片綽綽有餘。
- **電源**：每櫃**獨立 DC 供電**（7~24V，依鎖規格選 12V/24V）；485 只走訊號線，不共電。程式逐格開鎖天然分時，PSU 容量依「單鎖瞬間電流 × 同時開鎖數」估算。
- **線材**：A/B 雙絞遮蔽線＋GND 第三芯；櫃間走線避開動力線。9600bps 下櫃間幾公尺~幾十公尺沒壓力，不需中繼器。
- **驗收**：新板到貨先 `python3 tools/skb_probe.py sweep` 驗 485（吸取上次 SKB25 兩片收發器故障的教訓）→ 逐位址 `DD` 讀 MCU ID（1、2、3 各回一組 ID）確認定址 → `E2` 逐格開鎖實測。
- **替代方案**：若廠商 SKB36（V1.2）已停產，改每櫃 2 片 SKB18（18+18=36 路），位址每櫃佔 2 顆（總共 5 片、5 顆位址），其餘接法相同。

### 3.2 資料模型擴充（與穿線共存）
- 穿線現有：`pickup_codes`（取件碼，綁 venue）。
- 新增 `inventory`（販售庫存）：`venue_id, cabinet_id, slot_no, sku, name, price, qty, expiry_date(泡麵用), status(有貨/缺貨/故障/補貨中), updated_at`。
- 新增 `sale_orders`（販售訂單）：`order_no, venue_id, slot_no, sku, qty, amount, pay_status, open_status(已開格/卡貨), created_at`。
- 分店營收報表要能分「穿線收入／販售收入」。

### 3.3 交易流程（重點：**先付款後取貨**，跟穿線「先送件後取件」相反）

```
客人（LINE Rich Menu 或現場 kiosk）
  ① 瀏覽商品清單（含庫存、價格）
  ② 選商品＋數量 → 產生販售訂單（status: pending_payment）
  ③ 付款：LINE Pay v3（沿用 booking 骨架）
       ├─ 成功 → 送「開格指令」（RS-485）→ 客人取貨 → 完成
       └─ 10 分鐘未付款 → 自動釋放（比 booking 的 24h 保留短）
  ④ 付款成功但開格失敗 → 後台「卡貨處理」：一鍵退款 or 人工開門
```

### 3.4 與穿線共用（不重造）
- 同一個後台 `/admin`、同一份 LINE 通知（取件碼＝穿線；購買完成＝販售）。
- 補貨 SOP：後台看庫存 → 現場補貨 → 更新數量（掃碼或手動）。

## 四、泡麵 24h 特殊點（避坑重點）

1. **保存期限**：`expiry_date` 控管，過期格口自動標「不可售」，後台列出快過期清單。
2. **衛生**：只賣**乾貨碗麵**（無冷藏需求）→ 櫃子不需保溫改裝；不賣需冷藏的。
3. **補貨頻率**：泡麵週轉快，每週至少補 2 次；後台庫存預警（低於 N 件 → LINE 通知老闆）。
4. **定價**：整數定價（如 65/75 元），方便 LINE Pay 收付。
5. **防卡貨**：泡麵最容易卡在格口 → 現場驗收要做「掉得出來」深度測試。

## 五、閉環互補（為什麼兩個櫃一起才有意義）

- 晚上來寄拍（穿線櫃）→ 順手買泡麵（販售櫃）→ 隔天取拍。
- 等拍期間（30 分鐘～隔天）不餓 → 「24h 無人店」體驗才成立。

## 七、風險與避坑清單

1. **卡貨（最常見）**：開格後偵測取貨；超時 → 後台卡貨單＋LINE 通知老闆。
2. **退款**：付款成功、開格失敗 → 後台一鍵退款（LINE Pay API）。
3. **盤點對帳**：每日結算 = 系統販售收入 vs 實際減少庫存；差異 > 2 件要查。
4. **防竊**：販售櫃放監視器範圍；格口「一開一取」。
5. **泡麵過期**：expiry 控管＋補貨先進先出（FIFO）。
6. **現金**：暫不收現金（只 LINE Pay），避免找零/點鈔。
7. **硬體故障**：沿用 AnyDesk 遠端＋現場開門 SOP（`明天到現場_一次做完.md`）。
8. **共用庫地雷**：改 schema 仍守「**絕不 db push**」（booking 與穿線共用 Neon）。

## 十、Phase 1 運作紀錄（2026-08-21）

- **登入**：`/admin/login`。密碼存在 **資料庫**（`admin_credentials` 表，scrypt 雜湊），後台 **`/admin/password` 可直接改密碼**（像 booking 一樣）。
- **種子**：`node scripts/seed-admin-password.mjs`（DATABASE_URL＋NEW_ADMIN_PASSWORD）；Vercel 的 `ADMIN_PASSWORD` 只當首次種子來源，之後以 DB 為準。
- **env**：Vercel 需設 `SESSION_SECRET`（簽 cookie）。
- **後台**：`/admin`（穿線訂單）＋ `/admin/inventory`（庫存：售價/進價/數量/安全存量/上下架）＋ `/admin/purchase-orders`（進貨單：從低庫存一鍵帶入→入庫）＋ `/admin/stocktakes`（盤點）＋ `/admin/reports`（報表＋手動 LINE 檢查）＋ `/admin/suppliers`（供應商，LINE ID 窗口）＋ `/admin/password`（改密碼）。
- **前台**：`/store` 從 `inventory` 表讀真資料（缺貨/有貨徽章）；`GET /api/store/catalog` 給 kiosk 用。
- **已驗證**（本機＋正式站）：未登入 `/admin`→307 登入頁、`/api/admin/*`→401；登入→cookie；改密碼（驗證目前→更新→新密碼可登入、舊密碼失效）；登出清 cookie。
- **地雷提醒**：`/api/orders`、`/api/slots`、`/api/report` 等讀取 API 仍公開（穿線流程共用）→ Phase 1b 處理。
- **LINE 通知**：低庫存推播需要「有效 bot userId」——LINE Login 的 userId ≠ Messaging bot 的 userId。取得方法：用 LINE 私訊 bot 傳「**我的ID**」，bot 回傳 userId，再填入 `STAFF_LINE_USER_ID`（Vercel＋.env.local）。⚠️ 目前設定值無效（400 invalid 'to'），待老闆用「我的ID」取得正確值。
