# 架構評估：Pi 智慧拍櫃（5 家店）

> 針對 `pi/README.md` 的架構完整性分析。

---

## 整體判斷

### 架構設計品質：前段班

「前 10%」指的是**設計決策的成熟度**，不是完成度。具體來說：

- 「5 家店從第一天開始設計」而不是先做一家再改
- 「開鎖路徑不得依賴網路」的熱 / 冷路徑分離
- 協議層自帶模擬器、無硬體也能完整測試
- `config.ini` 是唯一差異——這條規則本身就是架構紀律
- 硬性規則明文寫出來（不洩漏 PII、不憑記憶寫協議）
- README 自帶「貼給 AI 的摘要」——考慮了協作場景

這些不是技術難度多高，而是**思維上的完整性**——大部分小型 IoT 專案不會在這個階段就考慮遠端維運、多店同步、離線容錯、接手文件。

## 關鍵風險與建議

### 1. MQTT 遷移時機

README 已明確標註「第二家店上線前應該換成 MQTT」。建議在第一家店穩定後、第二家硬體到貨前，先把 MQTT 通道做出來並灰度測試。這樣第二家直接走 MQTT，不用經歷遷移陣痛。

### 2. SD 卡壽命

`codes.cache.csv`、`pickups.queue`、`remote_done.json` + journalctl 都是寫入點。兩個低成本對策：

- 寫入頻繁的檔案掛到 tmpfs（重開機從 Sheet 重建）
- `journalctl` 設定 `SystemMaxUse=50M`，或轉到 tmpfs

### 3. 版本可見性

在 `/health` 回應裡塞 commit hash：

```bash
echo $(git rev-parse --short HEAD) > /opt/skb/pi/version.txt
```

這樣能一眼看出每家店跑哪個版本。

### 4. Chromium Kiosk 風險

觸控螢幕 + Chromium + Pi GPU driver 組合最容易出問題。優先測：

- 開機 → Chromium 全螢幕 → 觸控輸入
- 閒置 30 分鐘不鎖屏 → 觸控仍然正常

### 5. 災難復原

SD 卡掛了怎麼快速重建？至少需要：

- Pi OS 燒錄 SOP
- install.sh 一鍵恢復
- config.ini 備份位置

---

## 結論

架構的**思維品質**在前 10%，但**實作完成度**大概 40%。好消息是：難的部分（協議移植、離線容錯、多店設計約束）已經做完了。剩下的主要是體力活——MQTT 實作、硬體測試、監控腳本——而不是需要推翻重來的架構問題。
