## 協議摘要

RS-485，預設 9600 / N / 8 / 1。幀格式：

```
55 A1 <位址> <功能碼> <長度> <資料...> <XOR>
```

| 功能碼 | 用途 |
|---|---|
| `DF` | 廣播尋址（位址必須用 `FF`） |
| `D0` / `E0` | 讀 / 寫系統配置 |
| `D1` / `E1` | 讀 / 寫通道通電 |
| `D2` | 讀通道信號（門磁：斷開=門開） |
| `E2` | 開鎖 |
| `E4`/`E5`/`E6` | 電機模式（掛拍螺桿出貨用） |
| `A0` | 自動上傳（板 → 主控） |

完整定義見 `docs/skb-doc.txt`。**不要憑記憶寫幀格式。**

## 快速開始

### 開發（Mac / 任何機器，免硬體）

直接用瀏覽器打開 `kiosk/web/index.html`。橋接不在時會自動退回 DEMO 模式，
測試碼 `1234`（第 7 格）、`8352`（第 5 格）。

### 驗板（Mac，接上 USB-485 或 USB-TTL）

```bash
cd tools
python3 -m venv .venv && source .venv/bin/activate && pip install pyserial

python3 skb_probe.py ports      # 列出序列埠（macOS 系統 Python 受 PEP 668 保護，必須用 venv）
python3 skb_probe.py raw        # 送尋址幀，看有沒有回應
python3 skb_probe.py sweep      # 掃 5 種波特率
python3 skb_probe.py hunt       # 持續偵測，接對會嗶三聲 ← 換線時用這個
python3 skb_probe.py listen 20  # 只聽不送，按板子 RESET 測反向路徑
```

> ⚠️ **埠號會漂。** Win7 換 USB 孔就從 `COM3` 變 `COM5`；
> Mac 的 `cu.usbserial-1120` 後綴也是 USB 埠位置編號，換孔就變。
> 上樹莓派後務必用 **udev rules 綁 by-id**，固定成 `/dev/skb`、`/dev/labelprinter`。

### Win7 上線

見 `kiosk/README-kiosk.md`，完整四步。摘要：

```bat
src\build.bat                       編譯
SkbProbe.exe COM3 probe             驗板
SkbBridge.exe sim                   免硬體跑通整條流程
SkbBridge.exe                       正式（讀 sheet.ini）
```

### ★★ 2026-08-10 現場實測：頭號嫌疑是 USB-485 轉換器（已結案：轉換器沒事，見最終結論）

**轉換器有間歇性 USB 掉線的毛病，而且在兩台不同電腦上都發生過。**
一度以為它徹底死了（LED 熄、`ioreg` 完全列舉不到），拔插後又活了回來——
所以不是「死透」，是**接觸不良或供電不穩，且很可能收發級已受損**。

在這個前提下，**所有接線組合的測試結果都不可信**：送出去的訊號可能根本沒上線。

證據鏈：

| 時間 | 事件 |
|---|---|
| 前兩天 | 紅線接在轉換器 `A` 腳上約 48 小時 |
| 08-10 早 | Win7 上測到一半，`COM5` 憑空消失（`端口 "COM5" 不存在`） |
| 08-10 早 | 重插後回來，`ConfigManagerErrorCode 0 / Status OK`，但仍 0 bytes |
| 08-10 午 | 改用 Mac 測，`/dev/cu.usbserial-1120` 抓得到、埠開得起來，仍 0 bytes |
| 08-10 午 | Mac 上也憑空消失。**拆掉所有線、換 USB 孔，三次 `ports` 全空** |
| 08-10 午 | `ioreg -p IOUSB` 只列出 hub 和 HID，**完全沒有 CH340**，藍色 LED 也熄了 |
| 08-10 午 | 換 USB 孔後**又活了**（`cu.usbserial-1130`），LED 恢復 → 不是死透，是接觸/供電 |
| 08-10 午 | `hunt` 連跑 296 輪（約 8 分鐘）全 0 bytes，期間又出現 2 次 `Errno 6 Device not configured` |

**最合理的解釋**：紅線若帶 12V，連續兩天灌在 `A` 腳上，把收發晶片打成半死不活——
還能被 OS 列舉、埠也開得起來，但已經驅動不了差動線，所以**不管哪一種接法、
哪一種波特率、哪一台電腦，永遠都是 0 bytes**。今天終於完全失效。

> ✅ **好消息：鎖控板很可能從頭到尾都是好的。**
> ⚠️ **教訓：USB-485 / USB-TTL 這類小轉換器一律買兩支。** 備品比除錯時間便宜太多。

#### ★ 官方端口圖判讀（2026-08-10，取自原廠 docx，已存進 `docs/`）

原廠《锁控板技术文档 V3.1》的 **UPUS-SKB25-V3.0 接口端口图** 白紙黑字寫著：

| 接口 | 絲印 | 用途 |
|---|---|---|
| **P2 綠色端子（右側兩顆螺絲）** | **`A+` `B−`**，下方標 **`485`** | ★ **主要 485 接口，就是這個** |
| P1 綠色端子（左側兩顆） | `+` `−`，下方標 `電源` | 電源輸入，**不可接到轉換器** |
| 白色 6P 座 | `GND` /（空）/ `A+` `B−` / `VCC` `GND`，旁標 **`級聯`** | 串接第 2、3 塊板用；也帶 A+/B− |
| **UART 排針** | **`5V` `Rx` `Tx` `Gnd`** | ★ TTL 第二條路就是這裡 |

參考圖：`docs/skb25-port-map.png`（全板）、`docs/skb25-485-terminal.png`（綠端子特寫）、
`docs/skb25-cascade-uart.png`（級聯座 + UART 排針特寫）。

**重點一**：白色 6P 是「級聯」口，不是主 485 口。它確實也帶 `A+`/`B−`，
但**主口就在旁邊的綠色端子上，而且腳位標得毫無歧義**。之後一律接 P2。

**重點二**：級聯座只有 **5 支腳有針**（右上角是空的），正好對應現場那條 5 芯壓接線 ——
`GND` / `A+` / `B−` / `VCC` / `GND`。所以 **紅黃綠三條 = A+ / B− / GND 的某種排列**，
兩條黑 = `VCC` / `GND`（走 DC 圓頭）。

**重點三**：`DF` 廣播的正確回應是 `55 A1 FF DF 01 01 D4`（原廠文件範例），
與 `SkbProbe` / `skb_probe.py` 送出的 `55 A1 FF DF 00 D4` 完全對應。**協議側再次確認無誤。**

> ⚠️ **TXD 燈會閃 ≠ 轉換器沒問題。**
> 2026-08-10 實測轉換器 TXD 燈隨每 1.5 秒的送出規律閃爍——但那只證明
> **USB-Serial 晶片有把資料丟給 RS-485 收發晶片**，不證明收發晶片有把訊號打上 A/B 差動線。
> 「TXD 有閃、但線上沒訊號」正是收發級被過壓打壞的典型症狀。

#### ★ 壓接線的線色定義（2026-08-10 用萬用表通斷法實測，不是推測）

把 6P 壓接線插在 25 路板上、板子斷電，量「線頭 ↔ 綠色螺絲端子」的通斷：

| 線色 | 對 `A` 螺絲 | 對 `B` 螺絲 | 結論 |
|---|---|---|---|
| **紅** | **通（0Ω）** | 不通 | **= 485-A** |
| **綠** | 不通 | **通（0Ω）** | **= 485-B** |
| **黃** | 不通 | 不通 | **= 485-GND** |

**這證實了兩件事**：

1. 白色 6P 座與綠色螺絲端子在板內是**同一條 485 線路**
2. **專案最初的接法（紅→A、綠→B、黃→GND）從頭到尾就是對的**——
   線從來沒接錯過。當時失敗是因為那支 USB-485 轉換器已經半死
   （後續兩次從 USB 憑空消失、LED 熄滅可證），而為了排除接線，
   反而把原本正確的接法拆掉了。

#### 50 路板（第二塊板，2026-08-10 取得）

規格與 25 路板不同：**50 通道（CH01~CH50）、無撥碼開關，改用七段顯示器 +
`設置`/`▲`/`▼` 三鍵設定位址、另有 `一鍵全開` 按鈕**。

#### ★★★ 2026-08-10 最終結論：協議文件與實際板卡不符

**串口層已經徹底窮盡，全部無回應：**

| 變數 | 已測範圍 | 結果 |
|---|---|---|
| 波特率 | 1200 / 2400 / 4800 / 9600 / 19200 / 38400 / 57600 / 115200 | ✗ |
| 校驗位 | N / E / O | ✗ |
| 停止位 | 1 / 2 | ✗ |
| 位址 | 廣播 `FF` + 點名 1~32（DD）+ 1~8（D0） | ✗ |
| A/B 極性 | 兩種 | ✗ |
| 板卡 | **25 路與 50 路兩塊獨立板卡** | ✗ |

`deep` 模式共測 **48 種串口參數組合**，加上位址與極性的交叉，全數為零。

**同時，以下全部證實正常：**

- 匯流排電氣：A 對 B 量得 **34.2 kΩ**（RS-485 收發晶片輸入阻抗），訊號確實抵達板卡腳位
- 板卡 MCU：**存活**（`一鍵全開` 繼電器動作、七段顯示器正常、設置選單可操作 00~99）
- 工具鏈：兩支 USB-485 轉換器對接自測互通（一送一收，幀完全一致）
- 線色：萬用表通斷實測（紅=A、綠=B、黃=GND）

**最關鍵的一項觀察**：以一支轉換器**專職監聽**、另一支專職發送，
全程只收到我方送出的幀，**板卡從未發送過任何一個位元組**。
若板卡以其他波特率回話，9600 的監聽器會收到亂碼；但收到的是**絕對的零**。

#### 為什麼判斷是「協議不符」而非「板卡故障」

1. **兩塊不同型號的板卡行為完全一致**——同時發送端故障的機率極低
2. **實體板卡與《锁控板技术文档 V3.1》的圖片完全不符**：
   - 文件是**藍色 PCB**，實物是**黑色**
   - 實物有 `Bluetooth module` / `Ethernet module` 空焊區，文件無
   - 25 路板的 TTL 是 `TTL IO` 2×2 焊盤，文件是 `5V Rx Tx Gnd` 一排
   - **50 路板根本不在該文件內**（文件僅 SKB18 / SKB25 / SKB36）
3. 一塊正常的板卡收到看不懂的協議時，**正確行為就是完全不吭聲**

#### ★ 下一步：向廠商取得三樣東西

1. **兩塊板卡的完整型號**（板緣或背面絲印）
2. **對應型號的通訊協定文件**——現有的 V3.1 極可能不是這批板子的

| ✅ **.NET 接收層** | OS 層 `type COM3` 直讀也是零資料 |

#### 結論

**故障 100% 在物理層，而且不是 A/B 接反。** 軟體側已無假設可試。

#### ★ 最強假設：接錯線（2026-08-07 從照片判讀）

放大板子絲印後，白色 6P 座的腳位定義確認為：

```
        ┌──┐  ← 卡榫
┌───────┴──┴────────┐
│  (+)   (B)   (−)  │   上排
│  (G)   (A)   (+)  │   下排
└───────────────────┘
```

**這個座同時帶電源和 485**：兩個 `+`、一個 `−` 是電源，只有 `A` / `B` / `G` 是資料。

而實際從該座出來的線是 **黃、綠、紅、黑** 四條。紅配黑是電源線的標準配色。

**假設：紅=電源正極、黑=電源負極，真正的資料線只有綠和黃。**

過去兩天接的是紅、綠、黃 → 等於把 12~24V 電源接到轉換器的 A 腳，
真正的資料線只有一條在資料腳上。**從頭到尾沒有形成過有效的差動對**——
這完美解釋了為什麼五種波特率 × 兩種極性 × RTS 開關，全部都是 0 bytes。

> ⚠️ 反證：原廠「接線說明」圖裡，485 線畫的是綠/黃/紅三色。所以仍需實測確認。
> ⚠️ 若紅線確實是電源，它已接在轉換器 A 腳兩天。RJ201T3 有 TVS 保護，
> 大機率無恙，但不排除轉換器已受損——備一個替換品比較省事。

#### 下一步：桌邊暴力法（★ 板子在面前只要 2 分鐘）

未知數只剩一個：**四條線裡哪兩條是資料對**。4 選 2 = **6 種組合**，
每組試兩個方向，一組 10 秒，兩分鐘跑完全部。

**遠端做這 12 次要十二天，桌上做只要兩分鐘。這就是為什麼要帶去實驗室。**

```bat
2-findwire.bat          :: 雙擊即可，會自動編譯後進入找線模式
```

它每 1.5 秒送一次訊號，**接對了會嗶三聲**——眼睛看著硬體、手直接換線，
不用看螢幕、不用打字、不用重跑。第三條線接 GND2，換線不用停程式。

| 試這 6 組（各停 10 秒） |
|---|
| A=綠 B=黃 ／ A=黃 B=綠 |
| A=綠 B=紅 ／ A=紅 B=綠 |
| A=綠 B=黑 ／ A=黑 B=綠 |
| A=黃 B=紅 ／ A=紅 B=黃 |
| A=黃 B=黑 ／ A=黑 B=黃 |
| A=紅 B=黑 ／ A=黑 B=紅 |

**最可能的是第一組（A=綠 B=黃，黑接 GND2，紅不接）。**

#### 🔦 若 6 組全滅：改走 TTL（第二條路）

板子有 **TTL 擴充座**：`TTL 正極5V / TTL TXD / TTL RXD / TTL 負極`

**TTL 沒有 A/B 極性問題**——四條線、單端訊號、TXD 對 RXD、GND 對 GND。
今天卡的每一個問題（極性、色序、終端電阻、差動對）在 TTL 上都不存在。

需要一條 **USB-TTL 轉換器（CH340）**，約 50~80 元，跟現在這條 USB-485 是不同的東西。

接法：

```
USB-TTL TXD  →  板子 TTL RXD     ← 注意是交叉
USB-TTL RXD  →  板子 TTL TXD
USB-TTL GND  →  板子 TTL 負極
USB-TTL 5V   →  不接（板子自己有電）
```

協議完全一樣（`55 A1 ...`），所以 **`SkbProbe.exe` 不用改**，
直接指到新的 COM 埠就能用。

> 額外好處：TTL 正是 **300 間車隊架構（ESP32）的正式介面**。
> 走這條等於提前驗證車隊路線。見 Blueprint 附錄 C。

#### 若 6 組全滅（其他選項）

1. **改接綠色螺絲端子** — 板上綠端子旁有「120」跳線焊盤（RS-485 終端電阻的標準值），
   那很可能才是主要 485 接口。用自己的線接螺絲端子，跳過現成壓接線的所有嫌疑。
2. **換另一個白色 6P 座** — 兩個功能相同，30 秒可排除單一接頭故障。
3. **量 idle 電壓** — 板子上電、不送資料時，A 對 B 應有小幅正電位差。
   量到 0V 代表收發晶片沒在工作。
4. 換一個 USB-485 轉換器。
